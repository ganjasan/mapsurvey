## Context

Mapsurvey is a Django/PostGIS monolith on Render (`render.yaml` Blueprint; previews are manual and expire after a day because full-stack previews were 60% of the September bill). Support is Chatwoot with a "?" menu in the editor whose "FAQ" item points at a non-existent `/#faq` anchor. The SEO landings carry page-specific "why Mapsurvey" FAQs with `FAQPage` JSON-LD (`survey/landings.py`, `_faq_section.html`); those stay.

User-facing documentation does not exist. `docs/` is gitignored except `OVERVIEW.md`, `images/` and `research/survey-design-rules.md` — a 170-line, cited set of PPGIS design rules that already feeds the AI draft prompt (`survey/ai/prompts.py`) and the `newsurvey` skill. The local `docs/use_cases/` files are untracked product-idea notes with partner context, not publishable.

Audience: planners, consultants, researchers, educators — people who know their domain and often not GIS. Standards applied: Diátaxis (sections by reader mode), NN/g FAQ guidelines (real questions, user vocabulary, chunking, jump links), Google developer style (task headings in sentence case, numbered procedures, present tense), Good Docs Project templates (how-to, troubleshooting: symptom → cause → fix).

## Goals / Non-Goals

**Goals:**
- A help site that answers "how do I" before a human has to, reachable from the editor in one click.
- Pages that follow one convention each (tutorial, how-to, reference, troubleshooting, explanation, FAQ) so a page's shape tells the reader what it is.
- A Learn section that teaches participatory mapping as a practice and establishes Mapsurvey as the place that teaches it.
- Content maintained from evidence: page feedback, search terms, support conversations.
- Deploy and preview without touching the Django service; zero new cost.
- No dead links from the product into the help site, enforced by a test.

**Non-Goals:**
- Translations, a CMS, comments, versioned docs, a developer/API portal (the MCP reference is one page, not a portal).
- Replacing the landing FAQs or the in-app "What's new".
- Help Center inside Chatwoot.

## Decisions

### D1. Starlight in `help/` of this repository, separate Render static site

Starlight gives search (Pagefind), sidebar, i18n routing with fallback, sitemap, dark mode, accessible components and MDX for free. Same repository so a feature and its guide land in one PR and `help/**` is reviewable in the same place. Separate Render service so content ships without a Django deploy.

Alternatives: MkDocs Material (Python, but i18n via plugin and a documentation-tool look), Docusaurus (heavier, React, blog-centric), Mintlify/GitBook (hosted, paid for custom domain and theming, vendor lock), pages inside Django (ties content to app deploys, no search without work). A separate repository was rejected: cross-repo PRs for one feature.

### D2. Information architecture (Diátaxis) and URL scheme

```
/                      landing: search box, six section cards, "popular" list
/start-here/           one tutorial: first survey end to end (3–4 pages, numbered)
/how-to/<task>/        one task per page
/reference/<topic>/    question types, answers & exports, settings, sharing, MCP
/troubleshooting/<symptom>/
/learn/<topic>/        citizen engagement & participatory mapping practice
/use-cases/<case>/        one page per validated case, linking its story
/faq/                  single page, grouped, jump links
```

Folders are the sidebar groups (`sidebar: autogenerate` per directory, labels with `translations` for later locales). Use cases are a top-level folder, not a subfolder of Learn: Starlight labels an autogenerated subgroup with the raw directory name. Slugs are stable identifiers: the product links to them (D6) and `troubleshooting/<symptom>` slugs are referenced from error states (#295). Renaming a slug requires a redirect in `astro.config.mjs` (`redirects`).

Page shapes (templates in `help/CONTRIBUTING.md`):
- **How-to**: title "Verb the thing" (sentence case); one-line goal; "Before you start" (only if needed); numbered steps with one action each, screenshots after the step they illustrate; "Result"; "Related".
- **Reference**: tables and definitions, neutral tone, complete, no instructions.
- **Troubleshooting**: title is the symptom as the user sees it ("Autosave failed"); "Why it happens"; "What to do" (numbered); "If it keeps happening" → contact block.
- **Learn** (explanation): essays with headings, evidence cited, examples from stories, no product steps; link to the how-to that applies.
- **FAQ**: question in the user's words, answer ≤ 3 sentences, link to the full page. Groups: Getting started, Surveys & questions, Maps & layers, Responses & export, Sharing & embedding, Account & Pro, Self-hosting.

### D3. Learn section content

Sources: `docs/research/survey-design-rules.md` (tracked; remains canonical for the AI prompt and the skill — Learn pages are written from it and link to it on GitHub, so the three consumers do not drift), the public stories on mapsurvey.org (real examples), public PPGIS literature cited by name. Private notes in `../Mapsurvey-ops/docs/research/` may inform text but are not copied; no third-party PDFs/EPUBs are published.

Initial outline (titles are working titles):
1. What participatory mapping is, and when it beats a plain survey
2. Designing a map survey: one mapping task, points first, ask what works too
3. Writing questions people can answer on a map (sub-questions become columns)
4. Recruiting respondents: who shows up, who doesn't, and what to do about it
5. Reading the results: from pins to patterns, hot-spot caveats, small samples
6. Presenting results back to the public
7. Privacy and ethics: home locations, children, consent, open data
8. Use cases: one page per validated case, linking to the story

### D4. Theme and components

Starlight's default look reads as developer docs. Override with `customCss` (Mapsurvey palette and type from `base_landing.html`, lighter sidebar) and component overrides: `Header` (logo → mapsurvey.org, "Open Mapsurvey" button), `Footer` (feedback + contact block, D5), `Hero` on the landing (search-first). No React; Astro components only.

### D5. Feedback, contact and analytics

Footer override renders on every content page:
- "Was this helpful? 👍 👎" → `posthog.capture('help_feedback', {path, helpful})`; after a 👎 a one-line optional "What were you looking for?" text box.
- "Still stuck?" → link to `https://mapsurvey.org/?support=1` (the main site opens the Chatwoot widget when the query flag is present and the user is signed in; otherwise `mailto:CONTACT_EMAIL`). The flag handling is a small addition to `_support_chat.html`.
- Search terms: Pagefind UI has no hook, so a debounced `input` listener on the search field captures `help_search` `{query, results}` once per settled query.

PostHog: the main site's project with a `site: 'help'` property on every event, loaded through Starlight `head` from `PUBLIC_POSTHOG_KEY`/`PUBLIC_POSTHOG_HOST` build-time env. Unset → no snippet (same gating as the product). The help site is not respondent-facing, so the product-analytics "respondent pages are never tracked" rule is not touched.

### D6. Product → help links through a registry

`survey/help_links.py` maps keys to paths:

```python
HELP_LINKS = {
    'help_home': '',
    'reference_layers': 'how-to/add-a-reference-layer/',
    'embedding': 'how-to/embed-a-survey/',
    'pro': 'reference/plans-and-billing/',
    'export': 'how-to/export-responses/',
    'autosave_failed': 'troubleshooting/autosave-failed/',
}
```

A context processor exposes `HELP_URL` (a callable/dict built from `settings.HELP_SITE_URL`), templates use `{{ HELP_URL.reference_layers }}`. `HELP_SITE_URL` defaults to `https://help.mapsurvey.org`; self-hosters may point it at a mirror or empty to hide the links. A test asserts every registry path exists as `help/src/content/docs/<path>index.md|.mdx` (or the slug file), which turns a renamed page into a failing test instead of a dead link. The help menu's "Help centre" item uses `help_home` with `target="_blank" rel="noopener"`.

### D7. Deployment

`render.yaml` gains:

```yaml
  - type: web
    name: mapsurvey-help
    runtime: static
    rootDir: help
    buildCommand: npm ci && npm run build
    staticPublishPath: dist
    buildFilter:
      paths: [help/**]
    envVars:
      - key: NODE_VERSION
        value: "22"
      - key: PUBLIC_POSTHOG_KEY
        sync: false
    headers:
      - path: /*
        name: X-Content-Type-Options
        value: nosniff
```

Previews: none (`previews.generation: off`, owner decision 2026-10-13). Content is reviewed locally with `npm run dev`; DNS and the PostHog key are set up on production directly. The `IS_PULL_REQUEST` → `noindex` rule stays in the config as a safety net. Custom domain `help.mapsurvey.org` is declared in the Blueprint (`domains`); the DNS CNAME to the service's `onrender.com` host is added by hand.

Link integrity at build: `starlight-links-validator` fails the build on broken internal links, so a preview never ships a dead link.

### D8. Locales

`defaultLocale: 'root'` (`lang: 'en'`), content directly in `src/content/docs/`. A translated locale is added as `locales.<code>` plus a folder; untranslated pages fall back to English with Starlight's notice. Starlight emits `hreflang` alternates for locale pairs; verified in tasks before relying on it. UI strings for a locale go in `src/content/i18n/<code>.json`.

### D9. Help menu change

`_help_menu.html`: "FAQ" → "Help centre" (`fas fa-book-open`), href from the registry, new tab. Order stays: What's new, Help centre, divider, Help & support. The support-chat spec's requirement text is updated in the delta.

## Risks / Trade-offs

- [Looks like SDK docs, alienates planners] → theme and component overrides in D4; landing page is search-first with plain-language cards; review on the preview with a non-developer eye before switching the menu link.
- [Content rots; FAQ fills with invented questions] → FAQ rule (real sources only) and the feedback loop in D5; `lastUpdated` shown on every page; a quarterly pass over pages with the lowest "helpful" ratio.
- [Help menu switched before the site has enough content] → launch gate: tutorial + ≥ 8 how-tos + reference for question types and exports + FAQ seed + 3 Learn pages, all on the preview, before the Django change merges.
- [Product links drift as pages move] → registry test (D6) + redirects for renamed slugs + links validator at build.
- [Two FAQs (landing vs help) compete in search] → different intent: landing FAQ answers "why/should I", help FAQ answers "how"; cross-link, no duplication of questions.
- [Learn section accidentally republishes copyrighted research] → cite, paraphrase, link to publishers; the rules doc already follows this.
- [No preview to review on] → `npm run dev` locally; the links validator and the registry test catch the mechanical errors before merge.

## Migration Plan

1. Scaffold `help/`, theme, landing, section skeletons; Render service + domain on production.
2. Seed content to the launch gate above (content PRs can be several).
3. Django PR: `HELP_SITE_URL`, registry, help menu, "Learn more" links, support-flag handling, tests. Merge only after step 2 is live on `help.mapsurvey.org`.
4. Rollback: revert the Django PR (menu goes back to the old item); the help site can stay up harmlessly.
