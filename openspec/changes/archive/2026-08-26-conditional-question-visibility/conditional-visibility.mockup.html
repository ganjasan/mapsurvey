Conditional visibility — user journeys & mockups

Companion to proposal.md / research.md. Two grounding cases: Sodankylä (hand-written "Mikäli…" conditions, nine-neighbourhood grid) and Olney (one zone choice → one of ~10 zone sections). Styling mimics the current editor/respondent UI.

UJ-1 — Creator adds a question-level rule (Sodankylä "Mikäli…")

Maria, municipality employee; 41-question survey; writes conditions into question text because the product can't express them.
  1. Opens the editor, section 7, clicks ✏️ on "Mikäli toimit matkailualan yrittäjänä, mitä palveluita…" → question modal.
  2. Sees the new Visibility block below Required: ● Always shown ○ Shown conditionally.
  3. Picks "Shown conditionally": a Question dropdown (only choice/multichoice questions earlier in survey order, grouped by section) and Answers checkboxes. She picks "Toimitko matkailualan yrittäjänä?" = Kyllä.
  4. The live-preview column shows the condition chip: ⑂ Shown when: Toimitko… = Kyllä.
  5. Autosave. The question card in the structure list gets a branch badge (see UJ-3/UJ-4 screen).
  6. She deletes "Mikäli toimit matkailualan yrittäjänä, " from the question text — the condition now lives in the product, not the prose.
Success: respondents answering "En" never see the question; the 11-empty-rows artifact stops accumulating.
Edge: the survey is published and live. Saving a rule must not touch collected answers — it only changes who sees the question from now on.

UJ-2 — Creator hides a whole section (Sodankylä neighbourhood grid)

  1. Selects section 5 "Arvioi asuinalueita" (nine required neighbourhood ratings); the section detail form opens.
  2. Below Layout — the same Visibility block, identical rule shape: "Missä asut?" = the eight "I live here" options (any-of), leaving "Asun muualla" unticked.
  3. Saves; the section row gets a branch badge; hover shows the condition.
  4. Editor live preview as a respondent answering "Asun muualla": section 5 doesn’t appear between 4 and 6; progress shows the shrunken count.
Success: the 40%-“don’t know” matrix stops; the funnel stops losing respondents at the grid (the only mid-survey drop-off step). And: she has used the same rule UI twice — question, then section. Nothing new to learn.

UJ-3 — Creator builds the Olney fan-out (1 choice → 10 zone sections)

City Clerk digitizing the squirrel count. "Which counting area are you assigned to?" (10 options); each area has its own instructions + map extent → its own section. Exactly one of ten must show.
  1. Creates section 2 "Your area" with the choice question Area (10 options), and section 3 "Area 1 count" with area-specific content.
  2. In section 3's Visibility block: Question = Area, Answers = ☑ Area 1.
  3. The repetition problem — 9 more sections differing only in the ticked option. Two affordances:
    • Duplicate carries the rule: duplicating "Area 1 count" copies the visibility rule; she re-ticks one checkbox per copy.
    • Fan-out helper (screen B, bottom): when a section rule selects exactly one option and the controlling question has ≥3 options, the editor offers "Create one section like this per remaining answer (9)" — one click scaffolds Area 2…10, each pre-wired. (Design decision: v1 nice-to-have; if cut, cut the button, not rule-copy-on-duplicate.)
  4. The structure pane (screen C) reads as a visible branch: ten sections badged ⑂ Area = N. The badge is what keeps a 12-section list with a fan-out legible.
Success: a volunteer picking Area 7 sees exactly one zone section; progress counts 3 sections for them, not 12.
Edge — no rule matched: a respondent whose answer matches no section (creator forgot Area 10) flows past the fan to the next unconditional section — visibility semantics make "no match" safe, where jump semantics would dead-end. The editor still lints uncovered options (screen C, footer).
Edge — progress: section_current / section_total is computed over the sections visible for this session, recomputed when the controlling answer changes.

UJ-4 — Creator breaks a rule and is told (orphaned rules)

The MS-Forms failure class: edits silently breaking logic.

  1. She deletes option "Area 3" (or the controlling question; or drags the controller below a dependent; or moves the dependent to an earlier section).
  2. The dependent's badge flips to warning: ⚠ broken rule. The item is treated as always shown until fixed (fail-open — hiding content silently is worse than showing it), and the tooltip says so.
  3. Clicking the badge opens the Visibility block with the broken part highlighted.
  4. Same surface covers ZIP import: a rule referencing a missing question imports dropped + one report line, never a silent half-rule.

UJ-5 — Respondent: live show/hide within a section

  1. Section "About your count": "Did you spot any albino squirrels?" (○ Yes ○ No).
  2. The dependent "How many, and where exactly?" is absent — not greyed out, absent (state 1).
  3. Tap "Yes" → the card appears in place with a soft reveal (state 2). Back to "No" removes it.
  4. Answered "Yes" + filled the follow-up, switched to "No", hit Next: the client drops the hidden field; the server independently discards any answer invisible under the submitted answers — the Google-Forms back-button leak, closed at both layers.
  5. Required per consensus: a hidden question's required never blocks Next; the required-summary strip counts only visible questions.

UJ-6 — Respondent: section skip and Back

  1. After picking Area 7, Next goes straight to "Area 7 count" — the other zone sections never render. Progress reads the visible chain as bare numbers (owner decision): 2 / 3 on the area section, 3 / 3 on Area 7 — no “for you” hint.
  2. Back from "Area 7 count" returns to "Your area" (prev walks the same visible chain).
  3. Changing the answer to Area 4 + Next → "Area 4 count" (fresh); answers previously given inside "Area 7 count" are discarded server-side (no ghosts in export). v1 accepts silent discard on the abandoned branch — matching every researched platform; a "you'll lose answers" confirm is possible polish, not v1.

Journey-derived requirements not already in proposal.md

  1. Rule badges in the structure pane (question cards + section rows) — the fan-out is illegible without them (UJ-3).
  2. Duplicate carries the visibility rule — section and question duplicate (UJ-3).
  3. Fan-out helper — optional scaffold "one section per remaining answer" (UJ-3; design decision, may be cut from v1).
  4. Fail-open on broken rules + warning badge + import report line (UJ-4).
  5. Controlling-question picker constraints: only earlier-in-order choice/multichoice; moving/reordering re-validates (UJ-1, UJ-4).
  6. Lint for uncovered options on a fanned-out controlling question (UJ-3).
  7. Progress = visible chain, recomputed on controlling-answer change (UJ-3, UJ-6).
  8. Live preview respects rules and lets the creator play both branches (UJ-2).
